1. Introduction
1.1 Purpose
This document outlines the business requirements for the Ziggo platform. It details the features and functionalities of the system, capturing the user roles and behaviour to guide development and ensure the app meets all necessary requirements.
Version 3.1 realigns the BRD to mirror the PickMe feature set. All features are retained; features that were Ziggo-specific have been simplified to match the equivalent PickMe level of complexity (e.g. basic ride variants, simple rental booking, basic parcel delivery, a single truck option, simple promo codes, and a basic loyalty point system without tiers).
1.2 Background
Ziggo is an on-demand mobility platform designed to connect riders and drivers in a seamless experience. Unlike the model with separate apps for customers and drivers, Ziggo will have a single app for both parties, allowing users to switch roles through a button within the app.
Beyond ride-hailing, Ziggo operates as a multi-service app: parcel delivery (same-day Flash), food and grocery delivery, basic truck logistics, event discovery, in-app payments, and a simple loyalty programme are all delivered through the same client.
The platform consists of:
Single Customer-Driver App (Flutter)
Admin Panel (HTML/CSS/Python)
Backend System (Python)
VPS Server
Google Maps API for location tracking, routing, and ETAs
Firebase for notifications
PayHere for payment processing
2. Business Objectives

BO-2 | Enable users to switch between customer and driver roles via a button within the app.
BO-3 | Match ride requests efficiently and minimise wait times for both drivers and customers.
BO-4 | Ensure safe and traceable trips with ratings and trip records for both customers and drivers.
BO-5 | Allow operations to monitor the platform centrally via the Admin Panel.
BO-6 | Support multiple payment methods (cash, digital wallet, credit/debit cards) through PayHere.
BO-7 | Integrate Google Maps API for accurate location tracking, routing, and real-time ETA updates.
BO-8 | Use Firebase for push notifications for ride status updates, promotions, and other relevant alerts.
BO-9 | Offer multi-service delivery (food, market, parcel Flash, basic truck) from a single app.
BO-10 | Drive repeat use through a simple loyalty points system and promo codes.
BO-11 | Support basic business accounts for corporate ride and delivery bookings.
BO-12 | Surface third-party events to increase engagement.

ID | Requirement

5. Key Business Rules
ID | Requirement
BR-1 | A user can only be in one active role (passenger or driver) at a time.
BR-2 | Fare calculation includes base fare, distance, time, and surge pricing adjustments.
BR-3 | Cancellation after a grace period may incur a cancellation fee.
BR-4 | Users must be document-verified and admin-approved to operate as drivers.
BR-5 | Platform commission is deducted before the driver’s payout.
BR-6 | Loyalty points accrue on qualifying spend; refunded/cancelled transactions reverse the accrual.
BR-7 | Flash parcel delivery is same-day; basic courier handles longer distances.
BR-8 | Basic truck delivery is for moving goods within the service area; no size-tier categories or goods insurance.
BR-9 | Multi-stop trips allow a configurable per-stop waiting allowance (default 2 minutes); excess time is billed at standard waiting rates.
BR-10 | Basic membership benefits apply only while the membership is active.
BR-11 | Promo codes have defined validity windows and per-user usage limits enforced by the promotions engine.

6. Non-Functional Requirements
ID | Requirement
NFR-1 | Performance: Ride requests dispatched within seconds, real-time tracking updates.
NFR-2 | Scalability: Handle growing user base and concurrent trips across all service verticals.
NFR-3 | Availability: High uptime with fail-safe mechanisms.
NFR-4 | Security: Secure user authentication and payment handling (via PayHere); PCI-compliant card handling.
NFR-5 | Usability: Simple, intuitive flows for booking, driving, and role-switching.
NFR-6 | Localisation: Multi-language support (English, Sinhala, Tamil) and LKR currency formatting.
NFR-7 | Offline tolerance: Activity history and saved addresses cached for read access when the device is offline.
NFR-8 | Observability: All service flows (rides, deliveries, payments, loyalty) emit structured logs and business-event metrics.

7. Assumptions & Constraints
Users must have smartphones with GPS and internet access.
Google Maps API will be used for routing, location tracking, and ETAs.
Firebase will handle push notifications for ride status, promotions, and other alerts.
PayHere is the integrated payment gateway for digital payments.
Merchant partners (restaurants, market vendors) operate their own order-prep workflow and meet Ziggo’s preparation SLAs.
Event organisers list and manage their own events; Ziggo provides discovery only.
Push notification service providers are available.
8. Glossary
ID | Requirement
Trip | A single journey from pickup to drop-off.
Surge | Dynamic price increase during high demand.
Dispatch | Assigning a ride request to a driver.
Wallet | In-app balance used for payment.
Commission | Platform’s cut from the driver’s fare.
Loyalty Points | Points earned on qualifying spend, redeemable as a discount at checkout.
Flash | Same-day, on-demand parcel delivery service.
Courier | Standard parcel delivery for longer distances.
Flex | Premium car ride class with higher comfort.
Scan & Pay | Basic in-app QR code scanning for payment at supported points.
Multi-stop | A single trip with one or more intermediate stops between pickup and final drop.
Promo Code | A discount code applied at booking with a defined validity window and usage limit.
Rental | Hourly vehicle hire with a waiting driver.
